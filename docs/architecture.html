ARCHITECTURE · PRE-BUILD · v0.1

FairCart architecture

FairCart reads the shopping screen the consumer is already looking at, turns it into one normalised snapshot, and runs the same evidence-based rules on it whether the screen came from a Chrome tab or an Android app. A small backend adds what a single device cannot know: cross-store matches, shared price history and alerts. Everything that can run locally does.

Chrome extension · Android app · APITaxonomy: CCPA 2023 (13) + 15 sub-patternsSource: Indian e-commerce dark patterns report, 23 Oct 2026

Key decisions

These are the choices everything else depends on. Each one is explained further down.

One snapshot format for both platformsSite adapters (DOM) and app adapters (accessibility tree) both emit a ScreenSnapshot. Rules never see raw DOM or nodes.
Rules as data, evaluated twiceThe rule pack is versioned JSON with thin evaluators in TypeScript and Kotlin. One shared fixture suite runs against both, so the platforms can't drift.
Local first, AI optionalLayers 1–2 run on device with no network. Layer 3 (LLM) is off by default and only ever gets a sanitised excerpt of a single element.
TypeScript backend, shared schemasFastify + zod in the same monorepo as the extension. OpenAPI is generated from zod, and the Kotlin client is generated from OpenAPI.
Postgres as the price ledgerAppend-only, monthly-partitioned price_observation table. Each row records its source, so device, affiliate, licensed and demo data never mix.
Per-site opt-in permissionsThe extension declares retailer origins as optional_host_permissions and requests each one when the user enables that site. The Android service only receives events from enabled packages.
No server-side scrapingComparison data comes from what users open themselves, opt-in shared observations, and approved affiliate or licensed APIs. If none of these covers a store, the UI shows the gap.
Data residency in IndiaSingle region (AWS ap-south-1, Mumbai). No PII model: installs are anonymous IDs, which simplifies DPDP Act 2023 obligations.

System overview

Two clients on the left of the boundary do the reading and detecting. The cloud on the right only receives product identity, price facts and, if the user opts in, short element excerpts.

One engine, two sensors

The hard, research-driven work is the rules. Writing it once and running it on both platforms only works if both platforms feed it the same shape of data. That shape is the ScreenSnapshot.

The snapshot contract

type ScreenSnapshot = {
  platform: RetailerId; surface: 'web' | 'android';
  stage: 'listing' | 'product' | 'cart' | 'checkout' | 'membership' | 'account' | 'unknown';
  capturedAt: ISODate; adapterId: string; adapterVersion: string; readability: 'full' | 'partial' | 'none';
  product?: { title; brand?; model?; gtin?; mpn?; retailerSku; variant: Record<string,string>;
              seller?; condition?; quantity?: { value: number; unit: 'g'|'ml'|'pc'|'GB'… } };
  prices:    PriceFact[];   // listed, reference (MRP), per-unit, member-only — each with label text + elRef
  fees:      FeeFact[];     // kind: delivery|handling|platform|packaging|small_cart|cod|tip|donation, amount | null
  lineItems: LineItem[];    // title, qty, amount, origin: 'user_tap' | 'preselected' | 'unknown'
  controls:  ControlFact[]; // checkbox/toggle/button: label, checked, role (accept|decline), bbox, contrast
  cues:      CueFact[];     // countdown, stock, social-proof, sponsored-label, threshold-bar: raw text + parsed value
  total?:    Money;
  elRefs:    Record<string, LocalRef>;  // on-device handle to the element/node — never serialised off device
};

Rule pack format

Most rules can be written as a condition over snapshot fields plus journey facts. The few that can't, such as prominence ratios and countdown-reset tracking, are named built-in predicates that each platform implements and tests against the same fixtures.

{
  "id": "DRIP-02", "category": "drip_pricing", "subcategory": "late_mandatory_fee",
  "when":     { "stage": "checkout", "fee.kind": ["handling","platform","packaging","small_cart"], "fee.mandatory": true },
  "requires": { "journey.observedStages": ["product","cart"] },     // no claim if tracking started late
  "unless":   { "fee.disclosedAtStage": ["listing","product"] },
  "emit":     { "title": "Possible late checkout fee", "severity": "P0", "confidence": 0.8,
                "status": "needs_verification", "researchRefs": ["S1","S17","S18"] }
}

Rule packs are data, not code, so a new pack can ship from the backend without breaking MV3's ban on remotely hosted code. Each client also bundles a pack as a fallback, and it checks a downloaded pack's hash before using it.

Taxonomy → detectors

All 13 CCPA categories are in the taxonomy. Each has a signal it can fire on and an explicit case where it must stay silent. Severity uses the report's P0–P3 rubric. Categories that need a repeat test start as needs verification.

The research model stores each source (S1–S19) with an evidence level: regulatory finding, published audit, reported experience or pattern to test. A finding links to the category definition and its sources. It never links to a platform score, and historical platform findings are never used as a blacklist or as a prior.

Journey comparison

Layer 2 keeps a short, per-tab journey of snapshots for one basket and compares them. This fixture shows the evidence trail a user sees, including what was checked and not flagged.

  • Journey key: tab or task, retailer, and basket session. A journey resets on order confirmation, after 2 hours idle, or when the retailer or pincode changes.
  • Stored per stage: the snapshot minus elRefs and free text longer than 200 characters. Journeys live in memory and session storage and are dropped when the journey ends, unless the user saves the evidence.
  • User-tap ledger: the content script and AccessibilityService record clicks on controls FairCart has classified, storing only control ID and timestamp. This is how origin: user_tap is known. The ledger only observes and never synthesises or replays input.

Findings and their lifecycle

Finding schema (zod, mirrored by kotlinx.serialization)

Finding = {
  id: /* sha1(ruleId + platform + retailerSku + stage + evidenceKey) — stable across reloads */,
  ruleId, category: CcpaCategory, subcategory?: SubPattern, tags: SubPattern[],
  title: string,                // neutral: "Possible…", "Potentially misleading…"
  summary, consumerImpact, recommendedAction,
  evidence: [{ type: 'screen_text'|'price_change'|'control_state'|'journey_diff'|'history'|'ai_reading',
               description, source: 'current_page'|'journey'|'repeat_test'|'price_history'|'model',
               observedValue?, expectedValue?, stage?, timestamp }],
  evidenceBasis: 'current_screen' | 'repeatable_test' | 'published_audit' | 'consumer_report' | 'regulatory_finding',
  confidence: number /* 0–1 */, severity: 'P0'|'P1'|'P2'|'P3',
  status: 'detected'|'needs_verification'|'confirmed_repeatable'|'not_reproducible'|'dismissed_by_user',
  platform, surface, elementRef: LocalRef /* device only */,
  researchRefs: SourceId[], limitations: string[], disclaimer: string, detectorVersion
}

Layer 3: AI interpretation

  • Interface: ModelProvider.interpret(excerpt, elementMeta, candidateCategories) → AiReading. Calls go through the backend gateway, so keys never ship in either client.
  • Input: at most one element's text and its nearest label, sibling control labels, stage, and a few style facts. Before leaving the device the excerpt is stripped of digits longer than 4 (phone, card and OTP numbers), emails, names after "Hi" or "Deliver to", and addresses.
  • Output: forced JSON via tool or structured output, validated by zod: {category, evidence[], explanation, confidence, verificationSteps[]}. Each evidence quote must be a substring of the excerpt or the reading is rejected. AI readings are capped at needs_verification.
  • Provider: configurable. The default is Anthropic Claude (claude-haiku-5-5) for cost. Results are cached by excerpt hash for 7 days, and the excerpt itself is not stored. With no key, the UI shows "ambiguous, not analysed" instead of failing.

Price intelligence

The comparison is only as good as the match and the data. Both carry an explicit confidence and source, and a gap is shown as a gap.

Identity resolution ladder

TierSignalResult
1GTIN / EAN equalexact
2Brand + MPN/model + all variant axes equalexact
3Known cross-store listing pair (confirmed by users)exact
4Same model, other seller or conditionsame model
5Same model, a variant axis differs (128 vs 256 GB, 500 g vs 1 kg)variant differs
6Attribute fingerprint + title similarity onlysubstitute

Tiers 4–6 are never mixed into the "exact" list. Grocery pack sizes are normalised to a per-unit price (₹/kg, ₹/L) and compared only within the same pack size by default.

Ranking is by the lowest complete effective total. Affiliate commission is not an input to ranking. Any affiliate link is marked as one.

30-day low: when FairCart is allowed to say it

comparableKey = (productId, variantHash, sellerClass, condition, packQty, pincodeBucket?)  // pincode for quick commerce only
window        = observations(comparableKey, now − 30d … now), source ∈ {device, shared, affiliate_api, licensed}
coverageDays  = now − earliest(observations(comparableKey))
maxGap        = largest gap between consecutive observation days inside window

if (coverageDays ≥ 30 and maxGap ≤ 3d) or licensedSourceCovers(window):
    show "30-day low ₹X · n observations · sources"
else:
    show "Tracking began {coverageDays} days ago. A full 30-day low is not available yet."
    show "Lowest seen so far ₹X"  // never labelled 30-day
median  → only with ≥ 7 distinct observation days
chart   → plots observed points only, no interpolation; gaps drawn as gaps; estimates in a separate dashed series

Each provider reports provider_health (last success, last error, freshness). The comparison table separates "store not checked: provider unavailable" from "no matching offer found". An observation older than 24 h (marketplace) or 30 min (quick commerce) is shown as stale.

Checkout scanner and quick commerce

"Scan checkout" is a read-only pass over the current bill. It never clicks, removes, unticks or pays.

What it does

  • Parses every line on the bill into lineItems and fees with a fee classifier (handling, platform, packaging, delivery, small-cart, surge or rain, tip, donation, COD, convenience).
  • Recomputes the total. If the lines don't add up to "To pay", it shows "₹N not explained by any visible line".
  • Diffs the bill against the journey: new lines, preselected paid items, total changes against the last observed total.
  • Reads thresholds ("add ₹X for free delivery"), whether the condition is met, and what the "free" item actually costs.
  • Lists what it couldn't read, such as a fee row with no accessible text, and marks each item as confirm manually.

Quick-commerce specifics

  • Fee timeline per basket: the stage where each fee first appeared, and whether its amount or condition was shown earlier.
  • Default tip and donation checks: a pre-filled amount with no tap is tagged as a preselected default.
  • Pass or membership upsell: renewal price and cadence present or absent (SaaS billing), plus the decline-control prominence ratio.
  • Wallet credit: headline value compared with visible terms (cap, expiry, minimum spend).
  • ETA promises are recorded but never flagged on their own. They are only flagged if the ETA claim changes after payment intent with no explanation.
  • Sponsored shelf: label visibility per card. A paid slot with a clear label is not a finding.

Chrome extension

WXT + React + TypeScript, Manifest V3. WXT handles MV3 entrypoints, HMR and a Firefox/Edge build later.

Entrypoints

  • Content script (registered at runtime via chrome.scripting.registerContentScripts only for granted origins): adapter, extractor, L1 rules, tap ledger, markers.
  • Companion: a single closed Shadow DOM root inside the content script. It shows an orb near the cursor that is placed with requestAnimationFrame and only moves when the pointer rests for 250 ms, and a radial menu that flips to stay in the viewport and away from the hovered target's box. Keyboard: Alt+Shift+F opens it, arrow keys move between actions, Esc closes.
  • Service worker: per-tab state, journey store, alarms for watches, API client, side-panel sync bus.
  • Side panel (chrome.sidePanel, per tab): Dark patterns · Compare · History · Saved, plus checkout breakdown.
  • Onboarding + options pages: site toggles, sensitivity, companion behaviour, local-only mode, export, wipe data.

No <all_urls>, tabs, history, cookies or webRequest. Without the tabs permission, the panel learns the active URL from host permission on granted sites.

Performance rules

  • One MutationObserver per page, attached to the adapter's region roots (results grid, price block, cart summary) instead of body. It ignores mutations inside FairCart's own shadow host, so it can't trigger itself.
  • Debounce 400 ms with a 2 s max wait. Each snapshot is hashed, and an unchanged hash skips the rules.
  • SPA navigation is detected via the History API patch and navigation events, which start a new snapshot. A full reload starts a new page within the same journey.
  • Hover targeting: one delegated pointerover listener checks against a WeakMap of classified elements. There is no DOM scan on mouse move.
  • Budget: under 8 ms main-thread time per snapshot on a mid-range laptop, enforced by a perf test against the fixtures.

Android app

Kotlin, Jetpack Compose, Hilt, Coroutines/Flow, Room, DataStore, WorkManager, Ktor client with kotlinx.serialization. Modules split along the same boundaries as the extension.

Screen reading

  • FairCartAccessibilityService: packageNames is set at runtime with setServiceInfo() to only the apps the user enabled. Events: TYPE_WINDOW_STATE_CHANGED, TYPE_WINDOW_CONTENT_CHANGED and TYPE_VIEW_CLICKED (for the tap ledger). canRetrieveWindowContent=true, isAccessibilityTool=false.
  • Pipeline: foreground filter → 500 ms settle debounce → safety gate → bounded traversal (max depth 40, max 1,500 nodes, text truncated to 200 characters) → app adapter → snapshot hash → rules. Nodes are released immediately, and only the last snapshot per stage is kept.
  • Safety gate suspends and clears its cache on: any isPassword node; editable fields with OTP, PIN or CVV hints; known UPI and payment packages (verified with <queries>, not QUERY_ALL_PACKAGES); text such as "Enter UPI PIN", "CVV" or "OTP"; and screens that can't be classified. Typed text is never read.
  • Companion: drawn with TYPE_ACCESSIBILITY_OVERLAY from the service, so no SYSTEM_ALERT_WINDOW permission is needed. It shows a pill with states (idle, product found, issue, compare ready, checkout scan, paused, can't read). It can be dragged, snaps to edges, can be minimised, and long-press pauses it.
  • Manual fallback: "Analyse a screenshot" (photo picker) or a user-started MediaProjection single capture with the OS consent dialog and a foreground service of type mediaProjection. OCR runs on device (ML Kit), and the image is discarded after parsing. Secure windows come back blank and are reported as unreadable.
  • Share target: a shared product link opens the compare and history screens without any monitoring.

Play compliance

  • A prominent in-app disclosure appears before the Accessibility settings intent. It covers what is read, which apps, purpose, what stays on device, what is sent, retention, and how to turn it off. The user must tap an affirmative "Agree and continue", and declining keeps the app usable.
  • Play Console Accessibility API declaration, with a demo video of the disclosure and the read-only use.
  • The service never calls performAction on other apps' nodes or dispatchGesture. A lint rule and a unit test fail the build if either symbol appears in :a11y.
  • Data safety form: price observations (optional, anonymous), app interactions (on device), no financial info, no messages, no contacts.

Build plan

Each phase ends with something a person can install and use. Amazon and Flipkart go end to end before breadth.

1

Foundation

Monorepo, schemas, taxonomy package, rule-pack format and both evaluators, snapshot contract, Postgres migrations, Compose stack, Android module skeleton, verified package and URL list.

Exit: one fixture runs through both TS and Kotlin evaluators and produces the same finding.

2

Browser and app shells

Onboarding with per-site permission, companion orb, radial menu, markers, side panel with tab sync. Android disclosure, service setup, overlay pill, home screen, and all empty, loading, error, stale and unsupported states.

Exit: on amazon.in and in the Amazon app, the companion shows "product found" with an extracted title, price and variant.

3

Detection

L1 rules for all 13 categories, journey store and L2 diffs, tap ledger, finding lifecycle, dismiss and report, L3 gateway with schema checks. Positive and negative fixtures per category.

Exit: the fixture suite is green on both runtimes. The sample-shop instrumentation tests pass.

4
